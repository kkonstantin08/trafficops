# TrafficOps Implementation Plan

> **For agentic workers:** Use `superpowers:subagent-driven-development` to implement this plan with the execution policy in `AGENTS.md`. Steps use checkbox syntax. Пользователь назначил исполнителей GPT-6 Luna high и проверку оркестратором GPT-6.1 Sol medium после крупного этапа. Правила пользователя имеют приоритет над автоматическим запуском отдельных ревьюеров.

**Goal:** Воспроизводимый стенд TrafficOps на Ubuntu 24.04 с интерактивной панелью, наблюдаемостью и автоматическим откатом пробного релиза.

**Architecture:** Один узел kubeadm с Envoy Gateway направляет трафик к панели и двум версиям демонстрационного сервиса. Управляющий API читает Prometheus, собранные Fluentd логи и изменяет ограниченный набор ресурсов; состояние и журнал операций сохраняются в SQLite.

**Tech Stack:** kubeadm, containerd, Flannel, Envoy Gateway, Python/FastAPI, HTML/CSS/JavaScript, Prometheus, Fluentd, SQLite, shell/Makefile, Helm и GitHub Actions.

**Spec:** [Согласованная архитектура](../../architecture-proposal.md). Перед исполнением читать её и корневой `AGENTS.md`.

## Global Constraints

- Ubuntu 24.04 должна быть проверена фактически; VM пользователя — ARM64, RAM 4 ГБ. Достаточность ресурсов не подтверждена.
- Основная совместимая комбинация для подбора patch-выпусков: Kubernetes 1.36 и Envoy Gateway 1.9. Перед установкой проверить ARM64-образы; сохранить точные версии/digest.
- Все HTTP-проверки пользовательского пути и генератор трафика идут через Gateway.
- Откат: окно 60 секунд, минимум 30 запросов `v2`, HTTP 5xx больше 5%, проверка раз в 10 секунд, два превышения подряд. Параметры настраиваемы.
- Нет данных, устаревшие данные и недоступность Prometheus — неопределённость. Не расширять релиз автоматически и не считать отсутствие данных нулевыми ошибками.
- Дождаться полного окна текущего canary; ручной откат не зависит от Prometheus. После автоматического отката повторный canary запускается пользователем.
- Один экземпляр управляющего API, одна изменяющая операция за раз; состояние переживает перезапуск. Доступ к Kubernetes ограничен демонстрационным namespace.
- Светлая спокойная панель; фактические данные, доступность и читаемость. Дизайн через навыки, указанные в `AGENTS.md`.
- В Git нет секретов; управляющие действия требуют авторизации, Origin и CSRF. Произвольные внешние URL, команды и имена Kubernetes-ресурсов клиент не задаёт.
- Исполнители проверяют свои изменения целевыми проверками; завершённый этап проверяет оркестратор без отдельного ревьюера. Не запускать сабагентов для чтения, каждой правки или проверки.
- Подтверждения привязывать к ID требований. Доступность конфигурации, lint и mock-тесты не подтверждают живой кластер.

## Review Focus

1. Прерывание или повторный запуск установки: сохранить секреты, данные и работоспособность; проверка в этапе 1 и финальная проверка в этапе 4.
2. Пустые, старые, нечисловые метрики и данные прошлого релиза: исключить ложное решение об откате; тест решения в этапе 3.
3. Перезапуск API во время изменения маршрута: согласовать SQLite с Kubernetes и не выдать неподтверждённый успех; проверка в этапе 3.
4. Неавторизованная команда, CSRF или попытка направить трафик наружу: запретить изменение; проверки API в этапе 3.
5. Буферизация/ротация логов и сохранность томов: маркер должен попасть в файловую точку назначения и быть найден панелью; проверки в этапах 2 и 4.

## Этап 1: обязательная база и HTTP через Gateway

**Files:** конфигурация Python/образа; `demo/app.py`; `deploy/versions.env`, `deploy/base.yaml`, `deploy/gateway.yaml`, `deploy/envoy-values.yaml`; `scripts/bootstrap.sh`, `scripts/deploy.sh`, `scripts/verify.sh`, `Makefile`; `tests/test_demo.py`; первая версия `README.md`.

**Requirements:** K8S-001, APP-001–004, GW-001–004, DEP-003–006; DEP-001/002 подтверждать только запуском.

**Interfaces:**
- `GET /healthz` → 200; `GET /metrics` → Prometheus text. Эти пути исключены из статистики пользовательских запросов.
- `GET /demo` и `/demo/region/{east|west}` → JSON с `service`, `version`, `region`, `request_id`, `run_id`; версия берётся из `APP_VERSION=v1|v2`.
- Счётчик `trafficops_http_requests_total{version,status}` и histogram `trafficops_http_request_duration_seconds{version}`. Уникальные маркеры не становятся labels.
- Одна компактная JSON-запись access-лога на запрос, error-запись при HTTP 5xx; версия, маркеры и статус присутствуют в записях.
- Два Service и Deployment `demo-v1`, `demo-v2` в namespace `trafficops`; маршрут `demo-route` сначала имеет веса 100/0.
- `make bootstrap`, `make deploy`, `make verify`; внешний HTTP через NodePort Gateway, внутренний адрес Gateway передаётся будущему API установщиком.

## Этап 2: фактические метрики и собранные логи

**Files:** `deploy/observability.yaml`, `deploy/prometheus.yml`, `deploy/fluent.conf`; изменения deploy/verify/README; результаты в `docs/evidence/`.

**Requirements:** MON-001/002, LOG-001/002, APP-003, DEP-006, DOC-004; OPT-003/004 после подтверждения.

**Interfaces:**
- Prometheus доступен внутри кластера по Service; опрос demo `v1/v2`, Envoy и инфраструктуры каждые 10 секунд. API использует `/api/v1/query` и `/api/v1/query_range`.
- Для решений об откате нужны количество пользовательских запросов и HTTP 5xx `v2` за окно, состояние target и время последнего исходного sample. Время исполнения PromQL не подменяет свежесть исходной метрики.
- Fluentd читает containerd/CRI-логи только демонстрационных приложений, разбирает JSON и сохраняет записи в `/logs` на локальном PV. API позже читает этот том как read-only.
- Выгрузка логов из буфера — каждые 2 секунды; проверка маркера ожидает результат до 30 секунд. Сбор access/error проверяется отдельно.

- [ ] Установить один Prometheus с retention 24 часа и лимитом TSDB 512 MB, отдельным томом. Включить targets обеих версий, Envoy, node-exporter для CPU/RAM и kube-state-metrics для состояния Deployment/pod. Точные образы экспортёров добавить в `deploy/versions.env`; список фактических метрик зафиксировать в README.
- [ ] Подготовить Fluentd с CRI-парсингом, файловым буфером и JSON-выводом. Проверить используемые plugins/образ, права чтения логов и записи назначения. Проверка реальной CRI-записи должна сохранять маркер и версию; неполные записи нельзя молча терять.
- [ ] Настроить почасовые файлы назначения логов и удаление закрытых файлов старше 24 часов отдельным ограниченным сценарием очистки. Исключить активный файл/буфер из удаления; задать лимит буфера и наблюдаемую ошибку при переполнении. Проверить ротацию коротким контрольным интервалом с возвратом исходных настроек.
- [ ] Расширить `make verify`: targets доступны, PromQL возвращает данные, уникальный HTTP-маркер найден в файловой точке назначения после Fluentd. HTTP 500 на данном этапе можно породить выделенным тестовым HTTP-запросом с защищённым серверным маркером; не менять весь трафик `v1`.
- [ ] Оркестратор проверяет этап целиком: запрос → метрика Prometheus → собранная запись. Измерить использование RAM/диска; по результату установить requests/limits. Если 4 ГБ недостаточно, сообщить измерение пользователю до изменения ресурсов.
- [ ] Сохранить реальные доказательства и commit этапа. Работа Prometheus только с собственными метриками не завершает этот этап.

## Этап 3: панель, управление и автоматический откат

**Files:** `controller/*.py`, `web/*`, `deploy/controller.yaml`; изменения `demo/app.py`, deploy/verify; `tests/test_controller.py`, `tests/test_rollback.py`.

**Requirements:** согласованная панель и сценарии архитектуры; OPT-001/003/004/005; DOC-006/010.

**Interfaces:**
- `GET /api/overview`, `/api/metrics`, `/api/logs?marker=...&limit=...`, `/api/operations` — фактические данные и время обновления, с явным состоянием unavailable.
- `POST /api/login`, `/api/logout`; сессионная cookie и CSRF-токен. Для всех управляющих POST проверять сессию, Origin и CSRF.
- `POST /api/traffic/start {rate,duration,path}`, `/api/traffic/stop`; допустимы только пути демонстрационного приложения, частота 1–20 запросов/секунду, длительность 1–180 секунд и не более 3600 запросов. По умолчанию 10 запросов/секунду и 180 секунд; максимум 10 запросов одновременно.
- `POST /api/release/start`, `/api/release/weight {percent}`, `/api/release/rollback`, `/api/release/complete`; старт с 10%, percent целое 0–100, продолжение блокируется при неизвестных метриках. Завершение допускается после полного окна достаточных свежих данных без превышения порога.
- `POST /api/incident/errors {enabled}` — ConfigMap новой версии; `POST /api/incident/restart-pod` — один pod приложения, выбранный сервером. Тестовые ошибки читает `v2` из обновляемого config-файла; Deployment и endpoints метрик остаются работоспособны.
- `evaluate_canary(snapshot: dict, policy: dict, previous_breaches: int, started_at: float, now: float) -> dict`: `state=observe|rollback|unknown`, число последовательных превышений и причина. Snapshot: `requests`, `errors`, `sample_time`, `target_up`; policy: `window_seconds`, `min_requests`, `error_threshold`, `required_breaches`, `max_sample_age_seconds`. Свежесть по умолчанию не более 30 секунд. Сравнение порога строго `>`.
- `store.py`: `sqlite3` для состояния текущего релиза, сессий и журнала операций. Журнал хранит статус pending/running/succeeded/failed/interrupted, причину и показатели. Ограничить журнал 10000 последними завершёнными операциями; текущую операцию и состояние не удалять.

- [ ] Сначала написать `tests/test_rollback.py`: ниже порога → observe; первое превышение → observe; второе → rollback; ровно 5% → observe; меньше 30 запросов, возраст sample >30 секунд, target down, NaN/Infinity, незаполненное окно → unknown. Запустить `python -m unittest discover -s tests -p test_rollback.py` и увидеть отказ до реализации; затем реализовать чистую функцию и получить PASS.
- [ ] Реализовать ограниченные клиенты Kubernetes/Prometheus и SQLite-store. Валидация метрик и HTTP-ошибок не заменяется пустым успешным результатом. Секрет установки создаётся один раз; повторный deploy сохраняет его. Пароль хранить безопасно, session token — хешированным. Cookie HttpOnly/SameSite, Origin/CSRF проверяются сервером; настройка Secure зависит от документированного локального HTTP или TLS.
- [ ] Добавить `tests/test_controller.py` для запрета без сессии/CSRF/правильного Origin, диапазонов трафика, произвольного URL/ресурса, выхода поиска логов за разрешённый каталог и лимита выдачи. Использовать stdlib unittest и HTTP-клиент зависимостей приложения; не создавать отдельный тестовый framework.
- [ ] Реализовать одну очередь изменяющих операций и один background-процесс контроля. Записывать намерение перед изменением ресурса, затем подтверждать состояние Gateway и HTTP-путь. После restart сверять маршрут с сохранённым состоянием; прерванную серию трафика отмечать interrupted, не запускать её автоматически снова. Несовпадение релиза не исправлять вслепую: показать reconcile-required и обеспечить ручной откат.
- [ ] Проверить restart API между применением маршрута и записью успеха, ошибку Kubernetes и конфликт ручного/автоматического отката. Согласованный конечный маршрут обязателен; не обещать exactly-once операцию. При ошибке подтверждения не записывать succeeded.
- [ ] Реализовать конечный генератор трафика через Gateway и управляемые ошибки `v2`. Выполнять flush истории запроса и структурированное логирование без секретов. Значения новой конфигурации видны в приложении после обновления файла; не обещать мгновенное применение ConfigMap.
- [ ] Построить пять разделов светлой панели через согласованный дизайн-роутер. Поллинг данных раз в 5 секунд, timestamps и признаки устаревания; действия имеют pending/success/error. Графики используют данные Prometheus; логи приходят только из назначения Fluentd. Поддержать клавиатуру, labels, focus, reduced motion и текстовые статусы.
- [ ] Для собственного сайта применить обычную браузерную проверку согласно политике `AGENTS.md`: заранее оценить CloakBrowser и объяснить выбор stock Playwright для сайта без антибота. Проверить пять разделов и основные действия; не запускать лишние browsers или сабагентов для проверки.
- [ ] Оркестратор проходит canary с здоровой `v2`, затем с тестовыми ошибками: наблюдает метрики, автоматический откат, журнал и итоговые запросы к `v1`. Отдельно проверяет недоступный Prometheus, ручной откат и восстановление после удаления pod/API-restart. Сохранить результаты и commit крупного этапа.

## Этап 4: воспроизводимость, CI и комплект сдачи

**Requirements:** DEP-001–006, DOC-001–010, SUB-001–007; OPT-002, PREF-001/002 и подтверждённые улучшения предыдущих этапов.

**Interfaces:**
- `make verify` проверяет базу; `make verify-scenario` выполняет ограниченный полный сценарий с возвратом healthy-режима и маршрута `v1`.
- CI проверяет Python, shell syntax, YAML/манифесты с Gateway CRD-схемами и сборку образов amd64/arm64. Публичная сборка/публикация использует разрешённый GitHub context; секреты и доступ не обходятся.

- [ ] Собрать CI из уже существующих runnable проверок. Проверка сборки ARM64 не заменяет runtime на ARM64 VM. Развёртывание на VM участника не делать обязательной зависимостью CI экспертов.
- [ ] Написать README и отдельную инструкцию `docs/verification.md`: подготовка Ubuntu 24.04, команды установки, доступ с Mac по IP VM/NodePort, безопасное получение credentials, ожидаемые ответы/метрики/логи, сценарий панели, повторный запуск и восстановление. Явно перечислить ограничения single-node и локальных томов.
