# 01. Обязательные компоненты

### K8S-001 — Рабочий Kubernetes-кластер
Статус: обязательное. Источник: «Задание кратко»; «1. Kubernetes-окружение».

Требование: развернуть работоспособный Kubernetes-кластер. Среду и совместимый способ развертывания участник выбирает сам.

Проверка: получить ответ API кластера и статус его узлов; затем развернуть и проверить компоненты решения. Доказательство: команды и фактический вывод.

### APP-001 — Веб-приложение в Kubernetes
Статус: обязательное. Источник: «2. Демонстрационное веб-приложение».

Требование: развернуть простое веб-приложение, принимающее HTTP-запросы. Допускается готовое open-source приложение; собственная разработка дополнительных баллов не даёт.

Проверка: показать запущенные ресурсы и выполнить HTTP-запрос. Доказательство: состояние ресурсов, код ответа и вывод запроса.

### APP-002 — Однозначно проверяемый ответ
Статус: обязательное. Источник: «2. Демонстрационное веб-приложение».

Требование: HTTP-ответ приложения должен позволять однозначно проверить успешность запроса.

Проверка: сравнить полученный статус и содержимое ответа с ожидаемыми. Доказательство: команда, ожидаемый и фактический результат.

### APP-003 — Логи HTTP-запросов
Статус: обязательное. Источник: «2. Демонстрационное веб-приложение».

Требование: приложение формирует access-логи HTTP-запросов, доступные Fluentd или Filebeat.

Проверка: выполнить запрос с уникальным маркером и найти соответствующую запись на стороне приложения. Доказательство: запрос и запись лога.

### APP-004 — Доступный образ или материалы сборки
Статус: обязательное. Источник: «2. Демонстрационное веб-приложение».

Требование: container image публично доступен либо в репозитории есть все материалы для его сборки.

Проверка: получить образ без приватного доступа или собрать его только из материалов репозитория. Доказательство: команда и результат.

### GW-001 — Реализация Gateway API
Статус: обязательное. Источник: «3. Gateway API».

Требование: установить выбранную open-source реализацию Gateway API / Gateway Controller.

Проверка: подтвердить наличие и готовность контроллера. Доказательство: версии, команды и состояние компонентов.

### GW-002 — GatewayClass, когда требуется
Статус: обязательное при требовании выбранной реализации. Источник: «3. Gateway API».

Требование: настроить GatewayClass, если он требуется выбранной реализацией; иначе зафиксировать, почему он не нужен.

Проверка: проверить ресурс и связь с контроллером либо документацию выбранной реализации. Доказательство: вывод и ссылка.

### GW-003 — Gateway и HTTPRoute
Статус: обязательное. Источник: «3. Gateway API».

Требование: настроить Gateway и HTTPRoute, направляющий HTTP-трафик к Kubernetes Service приложения.

Проверка: проверить ресурсы, их связи и принятый маршрут. Доказательство: манифесты и фактический статус ресурсов.

### GW-004 — Доступ через Gateway API
Статус: обязательное. Источник: «3. Gateway API».

Требование: HTTP-запрос через настроенный Gateway должен достигать приложения и возвращать ожидаемый ответ.

Проверка: выполнить указанный в README запрос через Gateway, а не прямо к Service. Доказательство: адрес/команда, статус и тело ответа.

### MON-001 — Сбор метрик Prometheus
Статус: обязательное. Источник: «4. Мониторинг».

Требование: Prometheus собирает метрики как минимум одного компонента развернутого решения; соответствующий target доступен.

Проверка: проверить состояние target в Prometheus и наличие свежих samples. Доказательство: адрес target, статус и фактический результат.

### MON-002 — Запрос метрик
Статус: обязательное. Источник: «4. Мониторинг».

Требование: продемонстрировать получение собираемых метрик через Prometheus query.

Проверка: выполнить документированный запрос PromQL. Доказательство: текст запроса и непустой результат с временной меткой.

### LOG-001 — Сбор логов Fluentd или Filebeat
Статус: обязательное. Источник: «5. Логирование».

Требование: использовать Fluentd или Filebeat для сбора access/error-логов демонстрационного приложения и передачи их в выбранную точку назначения. Способ хранения и просмотра выбирает участник.

Проверка: подтвердить работающий сборщик, входящий поток и точку назначения. Доказательство: конфигурация и фактические записи.

### LOG-002 — Лог после HTTP-запроса
Статус: обязательное. Источник: «5. Логирование».

Требование: после обращения к приложению соответствующая запись появляется среди собранных логов.

Проверка: выполнить HTTP-запрос с уникальным маркером и найти запись в выбранной точке назначения. Доказательство: запрос, команда поиска и найденная запись.
