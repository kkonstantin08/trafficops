# Инструкции агентам проекта TrafficOps

## Цель и согласованная идея

Проект для кейса DevOps «MTC ENGINEER HACK». Цель пользователя — максимально сильная работа по критериям жюри и шанс на финал, с фактически работающей обязательной частью.

TrafficOps — лаборатория эксплуатации веб-сервиса. Демонстрационный сценарий: нормальная работа → выпуск новой версии → контролируемый сбой → диагностика по метрикам и логам → восстановление. Все части должны воспроизводиться экспертом по публичному репозиторию.

Согласованное направление функций:

- HTTP-приложение с однозначно проверяемыми ответами и несколькими маршрутами через Gateway API.
- Стабильная и новая версии сервиса: пробное переключение части трафика и автоматический откат по метрикам ошибок.
- Контрольные ошибочные запросы для демонстрации наблюдаемости.
- Сбор метрик Prometheus и запросы, подтверждающие фактические данные.
- Сбор access/error-логов Fluentd или Filebeat; поиск конкретного запроса по уникальному маркеру в точке назначения.
- Восстановление приложения после ограниченного сбоя и безопасный повторный запуск развёртывания.
- Автоматизированное развёртывание, проверки сценариев и CI.

Связать функции общим сценарием эксплуатации. Объём приложения должен помогать демонстрировать инфраструктуру: собственное приложение дополнительных баллов не даёт. Готовые open-source компоненты допустимы.

Архитектура согласована пользователем: один узел Kubernetes через kubeadm, containerd и Flannel; Envoy Gateway; светлая панель на HTML/CSS/JavaScript; управляющий API Python/FastAPI; две версии компактного HTTP-приложения; Prometheus; Fluentd с файловой точкой назначения; SQLite для состояния операций; shell/Makefile/manifests и Helm для установки контроллера; GitHub Actions. Подробности: [архитектура](docs/architecture-proposal.md). Не объявлять все примеры инструментов из кейса обязательными зависимостями.

## Согласованный формат интерфейса

Пользователь выбрал интерактивную веб-панель TrafficOps. В ней эксперт должен отправлять тестовый трафик, видеть версии сервиса, запускать пробное обновление или демонстрационный сбой и прослеживать восстановление. Развёртывание и проверки также должны быть доступны командами по инструкции.

Панель должна показывать фактические данные и результаты операций. Метрики получать из работающего Prometheus; собранные логи — из выбранной точки назначения после Fluentd/Filebeat. Данные интерфейса не подменяют доказательства обязательных требований.

Пользователь выбрал светлую панель со спокойным оформлением. Направление: светлый нейтральный фон, чёткая типографика, читаемые таблицы и графики, тонкие разделители, сдержанные цветовые акценты. Цвета использовать для состояний и результатов; ошибки обозначать также текстом. Для выбранного направления использовать `minimalist-ui` вместе с основными навыками роутера. Доступность, читаемость и удобство работы с данными имеют приоритет над декоративной анимацией.

Пользователь выбрал автоматический откат пробного релиза при превышении заданного порога ошибок. Оценивать отдельно трафик новой версии по фактическим метрикам Prometheus, с достаточным числом запросов и свежими данными. Согласованные значения по умолчанию: окно 60 секунд, минимум 30 запросов новой версии, доля HTTP 5xx больше 5%, проверка каждые 10 секунд, две проверки подряд. Значения настраиваемы. До оценки дождаться заполнения окна после начала текущего canary.

При откате возвращать трафик на стабильную версию и проверять результат переключения. В панели сохранять причину, время, использованные показатели и фактический результат операции. Недоступность Prometheus, устаревшие данные или отсутствие запросов показывать как неопределённость: не считать это нулевой долей ошибок и не продолжать расширение пробного релиза. Ошибку отката явно показывать; не отмечать восстановление до подтверждения. После отката повторный пробный релиз запускается пользователем, чтобы избежать циклических переключений. Предусмотреть также ручную команду отката.

Операции панели ограничить заранее определёнными действиями над демонстрационным приложением. Согласованы: ограниченный RBAC в namespace приложения, сессионная авторизация, проверки Origin и CSRF для управляющих действий, заранее заданные ресурсы и конечные серии трафика. Разделы панели: обзор, трафик, релизы, инциденты, диагностика. Произвольное управление кластером не разрешено.

## Обязательная техническая связка

Kubernetes, HTTP-приложение, Gateway API с работающим контроллером и маршрутом к Service, Prometheus, Fluentd **или** Filebeat, подтверждённый запуск на Ubuntu 24.04, автоматизация развёртывания и повторного запуска.

Helm, Kustomize, Terraform, Ansible, shell и Python перечислены в кейсе как допустимые варианты. Выбирать необходимый набор, а не устанавливать всё. Расширения реализовывать после работающей обязательной части и подтверждать отдельными проверками.

## Модели и распределение работы

Пользователь назначил следующую схему:

| Роль | Название пользователя | Идентификатор модели | Reasoning effort |
| --- | --- | --- | --- |
| Оркестратор | GPT-6.1 middle | `gpt-6.1-sol` | `medium` |
| Сабагенты и исполнители | GPT-6 Luna high | `gpt-6-luna` | `high` |

`middle` трактуется как уровень `medium`. Идентификаторы и поддерживаемые уровни сверены с официальной документацией: [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).

Этот файл задаёт предпочтения проекта; он сам не переключает модель уже открытого чата. При запуске исполнителя явно выбирать указанную модель и уровень, если инструмент поддерживает это. Если модель недоступна, сообщить пользователю и согласовать замену.

Оркестратор ведёт обсуждение с пользователем, определяет крупные этапы и границы задач, принимает изменения и сам проверяет законченную большую часть. Исполнитель реализует согласованную часть и проводит необходимые проверки своего изменения.

Правила делегирования:

- Обычно достаточно одного исполнителя на крупный этап. Параллельная работа уместна для действительно независимых задач с разными файлами.
- Не создавать сабагента на каждую мелкую правку, чтение файла, тест или замечание.
- Не запускать отдельных ревьюеров на каждую задачу. Завершённый крупный этап проверяет оркестратор самостоятельно.
- Исполнители не создают собственные цепочки сабагентов без отдельной необходимости, согласованной оркестратором.
- Передавать исполнителю конкретную цель, ID требований, границы файлов и условия готовности.
- Отчёт исполнителя: что изменено, какие ID покрыты, результаты проверок и оставшиеся ограничения. Не считать отчёт доказательством без просмотра реализации и результатов оркестратором.
- Исправления после проверки выполнять в рамках того же этапа, без нового круга независимых ревьюеров.

## Крупные этапы и проверка

После выбора архитектуры использовать крупные этапы: (1) кластер, приложение и Gateway; (2) мониторинг и логирование; (3) сценарии обновления, сбоя и восстановления; (4) CI, документация и сдача. Точные границы уточнить в плане реализации.

По завершении каждого этапа оркестратор читает изменения, сопоставляет их с требованиями и запускает достаточную целевую проверку. Полную интеграционную проверку выполнять на готовом стенде и после изменений, которые могут нарушить взаимодействие компонентов. Не повторять одинаковые проверки без нового риска или изменения.

В [06-acceptance.md](docs/requirements/06-acceptance.md) использовать только статусы `не проверено`, `выполнено`, `частично`, `не выполнено`. Для выполненного пункта обязательны ссылка на реализацию и фактическое доказательство с датой и средой. Наличие YAML, успешный lint или готовность отдельных pod не заменяет проверку полного пути запроса.

Конкретно подтверждать:

- HTTP-запрос через Gateway с ожидаемым статусом и содержимым ответа.
- Доступный target и свежие метрики, полученные Prometheus query.
- Появление записи контрольного HTTP-запроса в точке назначения логов.
- Полный запуск на Ubuntu 24.04 и повторное развёртывание с сохранением работоспособности.
- Реальную работу каждой заявленной дополнительной функции.

## Среда пользователя и инструкция проверки

У пользователя локальная VM в UTM на Mac. По предоставленному выводу терминала подтверждены ARM64 (`aarch64`), 4 vCPU и 3,8 GiB гостевой памяти (2,9 GiB available на момент снимка). Swap: 3,8 GiB, не используется. Корневой LVM-раздел: 30 ГБ, занято 15 ГБ, свободно 15 ГБ; отдельно `/boot` 2 ГБ и `/boot/efi` 1,1 ГБ. Пользователь сообщил выделение 40 ГБ виртуального диска; его полная ёмкость и нераспределённое пространство этим `df` не подтверждены.

Фактическая гостевая ОС подтверждена как Ubuntu 22.04.5 LTS (`VERSION_ID=22.04`). Пользователь явно выбрал оставить эту ОС и тестировать на ней. Подготовить отдельный режим разработки для Jammy, не устанавливать пакеты Noble в Jammy и не предлагать обновление ОС повторно без новой необходимости. Для DEP-001 по-прежнему нужен запуск на Ubuntu 24.04: успешные проверки на 22.04 не закрывают этот ID. [Доказательство preflight и выбор пользователя](docs/evidence/vm-preflight.md). Эти сведения — исходные ограничения, а не доказательство достаточности ресурсов для полного стенда.

Учитывать ARM64 и ресурсы VM при выборе образов и компонентов. Не заявлять совместимость архитектур или достаточность ресурсов без подтверждения. Изменение VM и установка компонентов в неё выполняются в рамках отдельно согласованного этапа развёртывания.

Пользователь ожидает отдельную понятную инструкцию проверки: подготовка VM, команды по порядку, ожидаемые результаты, поиск метрик и логов, проверка повторного запуска и восстановление после демонстрационных сбоев. Инструкция должна позволять пройти сценарий без догадок и ручного редактирования Kubernetes-ресурсов.

## Простота, безопасность и внешние действия

- Работать в режиме Ponytail full: сначала понять поток и существующий код, затем выбрать минимальное достаточное решение. Переиспользовать стандартные средства и установленные зависимости; избегать абстракций и инфраструктуры на будущее.
- Сохранять пользовательские файлы и посторонние изменения. Не публиковать реальные секреты или персональные данные.
- Демонстрационные сбои ограничивать компонентами стенда; документировать восстановление. Не затрагивать инфраструктуру других проектов.
- Фиксировать версии компонентов и источники установки. Избегать незафиксированных `latest` там, где они нарушают воспроизводимость.
- Обсуждать существенные продуктовые и архитектурные развилки с пользователем. Рутинные детали согласованного этапа решать самостоятельно.
- Писать пользователю по-русски, кратко и конкретно; различать написанную конфигурацию, проверенный результат и открытые вопросы.

## Правила веб-интерфейса и браузера

- Для создания или переработки веб-интерфейса применять `website-design-router`: направление через `gpt-taste`, ровно один уточняющий вопрос при действительно неоднозначном стиле, выбор остальных Taste/image-generation навыков по роутеру.
- При отсутствии `.openai/hosting.json` не подключать Sites автоматически. При наличии использовать Sites для совместимости, реализации, проверки и публикации, сохраняя визуальное направление роутера.
- Перед автоматизацией браузера оценить CloakBrowser через `cloakbrowser-browser-automation`. При защите от ботов, необходимости профиля/отпечатка или использовании AI browser agent сначала предложить CloakBrowser и дождаться подтверждения на установку или изменение зависимостей.
- Для обычного тестирования собственного сайта объяснить, что stock Playwright проще и надёжнее, а CloakBrowser — необязательная альтернатива.
- При одобренном CloakBrowser использовать CDP или `executablePath`, не запускать параллельно stock Playwright Chromium, привязывать CDP к `127.0.0.1`, хранить профили и секреты вне репозитория. Проверить запущенный браузер; не обещать обход защиты.

## Сдача

Полное решение и документация должны быть в публичном репозитории, доступны для клонирования без авторизации, в основной ветке `main`. Репозиторий должен оставаться публичным до публикации списка финалистов.

Готовить ZIP/RAR не более 18 МБ, названный фамилией участника; внутри `Ссылка.txt` только со ссылкой на актуальную ветку и `Паспорт.pdf` не более 4 страниц и 15 МБ. Все заявления паспорта подтверждать репозиторием и проверками.

Кейс указывает срок «4 октября 23:59» и запрет изменений ветки после этого времени. Год и часовой пояс не указаны: не придумывать их, уточнить перед сдачей. Подробности и постоянные ID — в [04-submission.md](docs/requirements/04-submission.md).
